# 网络代理 · 设计说明

`dsh-notpdpton-proxy` 让 **DSH 自身进程**的出站 HTTP(S) 走代理，并把「存在代理」
这件事写进提示词，让模型知道何时该用、在 shell 里怎么用。

本文记录实现为什么长这样，尤其是几个无法从代码表面看出来的约束。

## 一句话结论

生效通道是 `node:http.setGlobalProxyFromEnv()`，喂给它的是一个**合成环境对象**，
不是 `process.env`。这一条同时解决了「覆盖哪些网络栈」和「密码不泄漏」两个问题。

## 为什么是它

Host 进程的出站请求会走两条完全不同的栈：

| 栈 | 谁在用 | 手工装 undici dispatcher 能覆盖吗 |
| --- | --- | --- |
| undici 全局 dispatcher | `fetch`：模型 API、`web_fetch`、HTTP MCP | 能 |
| `http(s).globalAgent` | 自己构造 `http.request` 的 SDK | **不能** |

`setGlobalProxyFromEnv()` 装的是**两个**：既调用 `setGlobalDispatcher(new EnvHttpProxyAgent(...))`，
也替换 `http.globalAgent` 与 `https.globalAgent`。实测两条路径都会经过代理：

```
fetch('https://…')          -> 代理收到 CONNECT host:443
http.get('http://…')        -> 代理收到 absolute-form GET http://…
https.get('https://…')      -> 代理收到 CONNECT host:443
```

而它返回的 `restore()` 正好就是 Cordis effect 需要的 disposer 形状。

## 为什么密码不进 `process.env`

函数签名是 `setGlobalProxyFromEnv(env = process.env)` —— 它接受**任意对象**。
所以这里传的是一个新建的普通对象：

```js
http.setGlobalProxyFromEnv({ http_proxy: 'http://alice:p%40ss@host:8080', https_proxy: '…', no_proxy: '…' })
```

实测：装完之后 `process.env` 里一个代理变量都没有，而请求照常带
`Proxy-Authorization: Basic …`。这比「先写 `process.env`、装完再删掉」更安全 ——
后者依赖删除时机，而前者从一开始就没有写进去。

意义在于：shell 工具 fork 子进程时子进程继承 `process.env`。密码若在里面，
模型跑一条 `env` 就能看见。现在它只活在 `EnvHttpProxyAgent` 的闭包里。

## 分层：启动层 → 本组件 → restore

`dsh-http-proxy` 在启动时已经按用户自己的 `http_proxy` / `ALL_PROXY` 装过一层。
本组件是**叠在它上面**的第二层：

```
启动层 (launcher)          <- installGlobalProxy(policy)
   ↑ restore() 回到这里
本组件 (this component)    <- setGlobalProxyFromEnv(synthetic env)
```

关掉组件 = 调 `restore()` = 回到启动层，而不是回到裸进程。用户自己的代理配置不会被抹掉。

实测：叠第二层后 `restore()`，路由回到启动层的策略；再次安装又回到组件策略，可反复切换。

### 「直连」不是「什么都不做」

如果启动层已经装了策略，那么「不安装」不等于「直连」—— 启动层的代理还在生效。
所以 `mode: direct`（以及启用但没解析出代理时）会装一个 **`no_proxy: '*'`** 的 agent：

```js
{ no_proxy: '*', http_proxy: 'http://127.0.0.1:1', https_proxy: 'http://127.0.0.1:1' }
```

`127.0.0.1:1` 是保留端口，永远不会被拨号；它只是让 transport 有东西可装。
`*` 让所有请求绕过，于是覆盖了下层的策略，同时仍然可以 `restore()` 回去。

## 回环地址必须强制并入

原生匹配器**不会**自动绕过 loopback（实测：裸 `127.0.0.1` 目标会被送进代理）。
如果不强制并入，DSH 自己的 Web UI（`127.0.0.1:50100`）和 Connection 传输会被塞进代理，
形成路由回环。

所以 `localhost, 127.0.0.1, ::1, [::1]` 四项**永远**出现在有效绕过列表里，不可关闭。
`::1` 和 `[::1]` 都要写，因为 undici 会把裸 `::1` 读成 host `:` port `1`。

## 绕过列表：能表达什么、不能表达什么

原生匹配器的规则（实测，不是推测）：

| 写法 | 行为 |
| --- | --- |
| `*` | 全部绕过 |
| `example.com` | 精确匹配 + 所有子域 |
| `.example.com` / `*.example.com` | 同上 |
| `host:port` | 限定端口 |
| `10.*` / `192.168.*` | **不匹配** |
| `<local>` | **不匹配** |
| CIDR (`10.0.0.0/8`) | **不匹配** |

后三种是 Windows `ProxyOverride` 常见的写法，但 Node 的匹配器没有「部分标签通配」
和「无点主机名」的概念。本组件**不会**把它们悄悄传下去 —— 那样会看起来生效、
实际仍走代理。它们被丢弃，并在设置页明确写出来：

> 跳过列表中的「10.*」无法由 Node 的代理规则表达，已忽略。

`127.*` 同样被丢弃并报告，因为 `LOOPBACK_NO_PROXY` 只覆盖 `127.0.0.1` 这一个地址，
不是整个 `127/8`。

## 为什么没有 `Config`

插件从 `D:\Develop\...` 这样的外部路径链接进 profile。实测在这个位置：

```
undici                   -> MODULE_NOT_FOUND
@deepseek-ai/schemastery -> MODULE_NOT_FOUND
@deepseek-ai/dsh-tools   -> MODULE_NOT_FOUND
```

（经 profile 符号链接解析也一样。）而 `export const Config` 需要 schemastery。

所以 Host 半边**只用 Node 内置模块**，设置存到 profile 目录下的
`notpdpton-proxy.json`，由组件自己的 RPC 通道读写。好处是零依赖、可手改；
代价是不会出现在插件管理器自动生成的配置表单里 —— 设置页由本组件自己提供。

写入是原子的：新内容先落到 `.tmp`，再 `rename` 覆盖。半个文件会被下次启动读成损坏。

## 密码存在哪里

| 位置 | 内容 |
| --- | --- |
| `notpdpton-proxy.json` | 只有 `authUser`，永远没有密码 |
| DSH 凭据库 | 密码，键为 `DSH_NOTPDPTON_PROXY_PASSWORD` |
| `process.env` | 什么都没有 |
| 路由返回值 | `http://***@host:port`（`redactUrl` 的结果） |
| 提示词 | 同上，且只描述「需要认证」，不给值 |

浏览器半边**不直接调用 `ctx.remote.credentials`**，而是通过组件自己的同源路由
（`endpoint: 'secret'`）让 Host 代为读写：

- `describe` 只能回答「是否已配置 / 是否可写」，读不回值；
- `set` 只收非空密码，且要求设置里已有用户名（Basic 认证缺一半等于没有认证）；
- `unset` 之后**立刻重新 describe**，因为删掉已存值可能让环境变量里的回退值重新生效，
  直接报「未配置」就是谎报。

为什么不用 `ctx.remote.credentials`：那是**生成的 Remote 命名空间**，只有客户端半边显式声明
`remote` 服务才挂得上来。一个「只负责一块设置表单」的组件，不该因为客户端未来调整
Remote 的挂载方式就丢掉整段认证配置。既有路由已经过宿主自己的登录/Host 闸门、仅同源可写，
用它可以让密码和配置只走一条通道、只在一处鉴权。

顺带一个必须说清的两阶段语义：**存密码不等于生效**。凭据库和路由是两次独立写入，
只有再点一次「保存并应用」才会把新凭据装进 transport。界面因此有 `auth.pending`
（凭据库已更新、路由未应用）和 `auth.partial`（密码写成功但配置应用失败）两个状态——
这两种情况既不谎报成功，也不谎称凭据被回滚。

## 客户端怎么和 Host 说话（这一条踩过大坑）

第一版用了 `connection.rpc.handle`。它在浏览器半边**永远拿不到**：

- 静态加载的客户端半边跑在一个沙箱里，只提供 `fetch`、`ctx`、`React`、`styles`；
- 它没有模块加载器，所以**看不到 `connection` 服务**，`ctx.get('connection')` 返回
  `undefined`，`connection.rpc` 也就是 `undefined`；
- 结果是设置块渲染成空壳，而且**不报任何错** —— 界面上就显示「没有设置项」。

（`connection.rpc.handle` 服务的是另一类调用方；`host.call` / `harness.handle` 那套属于
「动态插件」，即从控制台粘贴代码创建的那种，本地 profile 里的包用不到。）

正确的通道是 **`webServer.register` 一个 exact 路由 + 客户端 `fetch`**，
`dshmarket` 就是这么做的。

安全上有两道闩，因为 exact 路由会在 `/api` 统一闩**之前**被匹配，不经过它：

1. `connection.requestRejection(request)` —— 宿主自己的 Host/Origin 检查与浏览器登录校验，
   和它的 API 走同一套。**按请求读**：`connection` 服务在异步初始化之后才构造，
   本插件挂载时它还不存在。
2. 自己的 loopback 兜底 —— 宿主老到没有 `connection` 时用 `Host` 头判断
   （`Host` 是恶意页面唯一伪造不了的请求头）。实测 `127.0.0.1` / `localhost` / `[::1]`
   放行，`evil.example.com` 与 `127.0.0.1.evil.com` 都是 403。

路由还做了三件事：只接受 POST、请求体上限 64 KiB、所有回复 `cache-control: no-store`。

## 提示词注入的投递位置与缓存代价

这段文字**不在 system prompt 里**。`systemPrompt.context()` 注册的是「运行时上下文」，
Host 把它作为一条独立的 **user 消息**投递，标题是 `Current runtime context`，和工作目录、
沙箱策略、文件策略并列。实测抓到的会话记录（`session-a01a1a7e`，第 3084 条事件）长这样：

```
Current runtime context. This snapshot supersedes earlier runtime-context snapshots.

Current working directory: "D:\\Develop\\dsh-notpdpton".

Network proxy
- This Harness process sends its outbound HTTP(S) traffic through http://127.0.0.1:10808 (source: custom).
...
```

这个位置是**刻意设计**的，而且正好躲开了上下文缓存问题。`dsh-agent-loop` 里两段策略说明了原因：

- **system prompt 走的是「能力感知的追加」**：能力足够的路由可以把变化后的非空文本
  **追加在缓存历史之后**（`appends changed nonempty text after the cached history`）；
  能力不足、序列断裂或者被清空时，才会改写第一个 system 节点、把后续节点清空。
- **运行时上下文走的是「只在变化时新增一条消息」**：`RuntimeContextProjection.project()`
  在渲染结果与上次保留的快照**完全相同**时直接返回 `undefined`（不产生任何事件）；
  只有内容变了才 `createUserMessage` 追加一条新快照。

对我们的意义：

| 情况 | 是否破坏缓存 | 原因 |
| --- | --- | --- |
| 代理配置没变、每轮重复渲染 | **不会** | 文本相同 → `project()` 直接不产出消息，前缀完全不动 |
| 改了设置（代理开关、地址、来源、告知方式、模板） | 会产生一条新快照 | 只有内容确实变了才追加，且是**追加**而不是改写既有前缀 |
| 每轮都改设置 | 每轮多一条消息 | 这是真实状态变化，不是我们的开销；缓存命中率在这里本来就没有意义 |
| 把这段文字写进 system prompt 中间 | **会** | 那才会让 105 位置之后的所有内容每轮失效 |

所以第二条结论：**只要 `text()` 的输出在配置不变时保持稳定，就不会有任何缓存代价。**
反过来，如果这段文字里放了时间戳、随机数、每轮变化的计数值，就会每轮新增一条快照消息，
那才是真正的浪费。当前实现里没有任何随时间变化的字段 —— 这是有意的。

## 为什么 `required: true`

`systemPrompt.context()` 默认注册的是**可选**运行时上下文，`suppressRuntimeContext()`
可以把它移除。用已存的会话日志实测：

| 预设 | 有 runtime context | 含代理通知 |
| --- | --- | --- |
| ptc | 是 | **是** |
| minimal | 是（工作目录、团队身份都在） | **否** |
| standard | 是 | 否（但会话都在启用前，无数据） |

`minimal` 是决定性反例：它收到了同一条投递里的其他内容，只丢了我们这一项。
注册顺序不由本组件决定，所以标 `required: true` 是唯一可靠的修法。

代价说清楚：标了 required 之后，任何预设都无法通过 `suppressRuntimeContext()` 忽略它。
这是一个取舍 —— 代理状态属于「模型不知道就会做错事」的环境事实，因此倾向必投。

## 为什么模板可编辑但不允许随意发挥

模板只能引用 `{{proxy}}`、`{{source}}`、`{{bypass}}`、`{{shell}}`、`{{state}}`、
`{{auth}}`、`{{settings}}` 这套**由当前策略算出来的事实**。

这样做是为了让「改了文案」和「谎报状态」无法同时发生：模板可以重新组织措辞、
增减条目、改语言，但拿不到任何未经策略解析的值。三个细节：

- **未知占位符原样保留**（`{{nope}}` 就显示 `{{nope}}`），而不是替换成空。
  拼错一个占位符时，设置页预览里能直接看见，而不是悄悄少一行。
- **空白模板等于内置文案**，所以「恢复初始模板」就是把字段清空；清空后编辑框显示的是
  带占位符的初始模板，内置渲染结果仍在预览里查看。
- **初始模板不是内置文案**：空模板时编辑框填入带 `{{…}}` 占位符的 `DEFAULT_TEMPLATE`，
  保存仍按空模板处理；只有实际编辑后才成为自定义模板。
- **预览由 Host 渲染**（`endpoint: 'prompt'`），不是浏览器里再算一遍。
  两处各写一份渲染逻辑，早晚会不一致，而这里不一致的后果是「界面显示的」和
  「模型收到的」不一样。

## 设置界面的信息结构

界面长这样，是因为代理配置有三个容易混淆的地方，布局必须把它们分开：

1. **「正在编辑的」和「正在生效的」不是一回事。** 顶部状态条只读 Host 最后一次回复，
   永远不反映草稿；改任何开关都只进草稿，底部标「有未保存的修改」，只有「保存并应用」
   才会真正切换路由。这样「我关了代理」和「代理其实还开着」不会看错。
2. **认证是一次独立的写入，但必须和配置一起生效。** 密码走凭据库，配置走设置文件；
   两者是两个事务。所以密码不会自己「自动生效」，而是和草稿共用同一个「保存并应用」，
   并在失败时区分「密码已写入但配置没应用」（`auth.partial`）—— 这种情况既不谎报成功，
   也不谎称凭据被回滚。
3. **没有「刷新」按钮，保存后自动重读。** 早期版本在一个只读诊断区里放了「重新应用」和
   「刷新状态」两个按钮，但两者都是把用户当同步器：重新应用与保存按钮做的事一样
   （Host 在保存时本来就会重读一切），刷新则是要求用户手动确认一次状态。
   现在保存成功后客户端会自己再读一次 Host 状态，只读区域（生效状态条、
   系统代理报告）因此总是描述**实际生效**的配置。
   这次重读失败时保持静默：保存已经成功，为一次后续读取弹错误只会让人以为保存失败了。
   重读期间用户如果又改了草稿，新草稿保留，只有状态被刷新。
4. **「测试连通性」测的是已保存的配置。** 草稿有改动时按钮禁用，并说明要先保存；
   这不是偷懒，是因为 Host 侧探针必须量的是**真实装上去的路由**（构造一个新 agent 去测，
   会在真请求失败时照样显示成功）。改动或保存后旧的测试结果立即作废，避免旧成功冒充新成功。

版面上沿用了 DSH 设置页本身那套排版——**行 + 发丝线**，而不是自成一体的卡片盒子：

| 区域 | 内容 | 为什么在这 |
| --- | --- | --- |
| 顶部状态条 | 状态点 + 结论词 + 来源标签 + 生效地址 + 未保存标记（嵌套面板） | 一眼回答「现在到底走不走代理」；它是只读区，永远不跟着草稿变 |
| 启用代理 | 一行开关：只控制 DSH 自身请求是否走代理 | 与注入开关独立；关闭时保留 DSH 原有网络设置 |
| 启用注入 | 一行开关，紧跟在「启用代理」下面 | 只控制是否注入会话提示词，不影响路由；代理未生效时不注入 |
| 代理来源 | 28px 分段控件（五个来源）+ 所选来源的一句话说明 | `direct` 与「关闭」是两件不同的事，必须能区分 |
| 地址 | 自定义/自动来源才出现的地址输入 | 与所选来源无关的输入框不再灰着占位 |
| 代理认证 | 折叠区：用户名、密码、清除已存密码 | 大多数用户不需要，但需要时是独一块 |
| 会话提示词与 Shell | **模板/预览同框切换** + 快捷占位符（单行）+ shell 告知级别 | 「代理控制」「提示词注入」「Shell 告知」是三个独立开关；同框切换让注入内容可见、可改，又不增加一块版面 |
| 高级设置 | 绕过列表（始终显示当前生效值，来源自有时只读）、分协议代理、测试目标 URL、测试按钮与结果 | 低频但必须可达，默认收起 |
| 保存行 | 未保存提示 + 「还原修改」+ 倒色「保存并应用」 | 一次提交，紧跟在它要提交的内容后面 |

只读诊断不再占一整块「运行信息」：取消该栏后，Host 报告的绕过规则被丢弃、设置文件
损坏、SOCKS5 实验特性等**可操作警告**仍以紧凑列表显示在状态条下方；正常状态不出现。

模板与预览共用同一个 160px 高的框：默认编辑模板，点「预览」原地切换为 Host 渲染的
注入文本，再点「返回编辑」切回；两个框同高，切换时框本身不移动。空模板时框内填入
带占位符的初始模板，而不是示例占位符或内置渲染结果；编辑后即成为自定义模板。模板下方的
快捷占位符保留，但不再带标题，并排成单行横向滚动，窄窗口下不会换行成两排；悬停按钮
会显示该占位符当前渲染出的值（空值会明确标出）。快捷占位符不依赖预览：编辑模板清空预览
后仍然保留，值来自状态快照；预览存在时优先用草稿值。排除地址框也直接填入
当前生效的绕过列表：来源自带列表（系统代理、环境变量）时只读，自定义来源空值时填入
生效值，有草稿时显示草稿并在下方标出生效值。

折叠区不是为了「藏起来」：`aria-expanded` / `aria-controls` 齐备，
摘要行会直接显示该区状态（「密码已保存」「已配置分协议代理」「注入：已开启 · Shell：仅地址（推荐）」），
所以收起时也能看出里面有没有内容。

具体的排版取值来自对已发布 GUI 的实测，不是自创：

- 开关 36×20、滑块 16、位移 16px；分段控件 28px 页签 + 4px 轨道 + 滑动指示块；
- 输入框 34px 高、`--dsw-radius-md`、`border-l4` 发丝线、`bg-layer-3`；
- 行标题 14/22、行描述 12/18；行分隔线用 `border-l2`，最后一行去掉；
- 焦点用 `--dsw-alias-state-business-primary`（不是品牌色）；输入框聚焦换边框而不是画光圈；
- 提交按钮用倒色（`label-primary` 底 + `bg-layer-3` 字），不是品牌色填充；
- 状态只用颜色 + 文字成对出现，圆点从不单独承载含义。

窄窗口（设置弹窗被拖窄，或 200% 缩放）靠容器查询 `@container npd-proxy (max-width: 520px)`：
分段控件从「五列一行」变成「两列换行」，双列输入并单列，诊断表并单列，按钮占满整行；
`min-width: 0` 与 `minmax(0, 1fr)` 保证长代理地址在任意宽度下换行而不撑破页面。
颜色只用主题 token，因此亮/暗主题自动跟随。

## 界面状态机的几个决定

浏览器半边把状态放在一个可观察的小模型里（`createSettingsModel`），而不是散在组件里。
这不是为了架构好看，是因为下面几种情况都会让「表单显示」和「实际配置」脱节：

| 情况 | 处理 |
| --- | --- |
| 语言切换导致 `t` 换身份 | 模型不依赖 `t`，只依赖自己；翻译变化不再重新拉取状态 |
| 保存密码后重新读状态 | 只刷新「已生效」部分，**不覆盖**未保存的草稿 |
| 两个状态请求乱序返回 | 递增序号，旧回复直接丢弃 |
| 组件卸载时请求还在飞 | `AbortController` 取消，迟到回复不写状态 |
| 请求永远不返回 | 18 秒（探针 12 秒）超时，进入可重试的错误态 |
| 连续点两次保存 | 第二个操作被 `busy` 拒绝，且不会重复写密码 |

模型同时是离线回归测试的接缝：`test/verify-proxy-ui.mjs` 注入假的 Host 与凭据库，
驱动真实状态转换（37 个场景）。这类测试能抓住「加载失败后按钮消失」「保存密码吞掉草稿」
「旧探针结果冒充新配置」这类问题，但它**不证明**真实页面长什么样 —— 视觉仍需人眼确认。

## 提示词

用 `systemPrompt.context({ name: 'network:proxy', order: 105 })`，夹在
`WORKING_DIRECTORY (100)` 与 `SANDBOX_POLICY (110)` 之间 —— 它描述的是运行时环境事实，
和沙箱策略同类，不是工具说明。

内容由 `text: () => …` 动态产出，所以改设置立即反映在下一轮，不需要重新注册 section。
`promptInjection: false` 时返回空字符串，**完全不出现**，不污染提示词。

`promptInjection: true` 仍以代理生效为前提：代理未生效时返回空字符串，**不注入任何内容**。
「启用代理」只控制路由，「启用注入」只控制告知；两者是独立设置，但没有生效代理时
注入没有可告知的状态，因此开关打开也不会产生提示词。

模板仍然只能引用当前策略算出的 `{{…}}` 事实。代理未生效时 `{{proxy}}` 为空，
`{{shell}}` 说明本组件不向 shell 提供代理设置，`{{state}}` 与 `{{auth}}` 为空；
此时模板不会渲染进提示词。

三种「Shell 告知级别」对应提示词里的三句话：

| 取值 | shell 里拿到 | 提示词说什么 |
| --- | --- | --- |
| `off` | 什么都不注册 | 「shell 拿不到代理设置，需要用的话让用户提供」 |
| `url`（默认） | `DSH_PROXY_URL`，无密码 | 「地址可用但没密码；遇到 407 就告诉用户，别要密码」 |
| `full` | `DSH_PROXY_URL`，含密码 | 「直接用就行」 |

默认选 `url`：密码不进模型上下文，也不进会话记录。

## 生效范围（重要）

**只有 Host 进程。** 具体是：

| 会走代理 | 不会走代理 |
| --- | --- |
| 模型 API 调用 | 渲染进程（浏览器窗口自身的请求） |
| `web_fetch` / `web_search` | 系统里其他程序 |
| HTTP 形式的 MCP 服务器 | `ctx.ssh` 连接 |
| 任何用 `fetch` / `http(s).request` 的插件 | 工具子进程（除非模型按提示词显式使用 `$DSH_PROXY_URL`） |

最后一条是设计而非疏漏：把代理交给子进程意味着要把密码交给它，而这与「默认不给模型密码」
冲突。想让子进程也走代理，把「告知方式」调到 `full`。

## 已知限制

1. **PAC 不支持。** 注册表里有 `AutoConfigURL` 时会在设置页报警并忽略。
2. **socks5 是实验特性。** Node 会打 `ExperimentalWarning`。`socks5h://` 与 `socks4://` 被明确拒绝
   （原生 transport 只认 `http:`/`https:`/`socks5:`，其余直接抛 `Invalid URL protocol`）。
3. **TLS 中间人**需要用户自己设 `NODE_EXTRA_CA_CERTS`，本组件只做提示。
4. **纯 http 目标会被隧道化**（`CONNECT` 到 80）。个别代理不支持这种形式，此时对 http 目标需直连。
5. **非 Windows 没有系统代理读取**：只会读环境变量。
6. **系统代理只在可能用到时才读。** 读注册表要起一个 `reg.exe` 子进程（本机实测
   52–74 ms），所以 `install()` 先过 `needsSystemProxy()`：组件关闭，或来源被钉在
   `custom`/`env`/`direct` 时，启动完全不读。只有 `auto`（可能落到系统）与
   `system` 会读。设置页在 `system` 来源下仍要显示读取结果，那一份由 status 请求
   懒读并去重，同样不在启动路径上。
6. **老运行时降级**：没有 `setGlobalProxyFromEnv` 时退回 `undici` + `EnvHttpProxyAgent`，
   只覆盖 `fetch`，设置页的「生效范围」会如实显示 `undici（fetch only）`。

## 验证

`test/verify-proxy.mjs` 离线覆盖：

- 设置归一化（缺字段、错类型、未知键）；
- 代理 URL 校验与凭据处理（编码、脱敏、剥离）；
- 绕过列表翻译（哪些能表达、哪些必须报告）；
- Windows `ProxyServer` 两种写法；
- 解析链（custom → system → env，各自独立、不混用）；
- 提示词（三种 Shell 告知级别、代理未生效时不注入、路由与注入设置独立，且永不含密码）；
- **真实路由**：起一个本地假代理与本地源站，断言 https 走隧道、loopback 直连、
  直连策略覆盖上层、`restore()` 恢复上层、以及 `process.env` 全程干净；
- 持久化（往返、损坏容错、不落密码）；
- 浏览器半边的注册、词典完整性与 block 渲染。

全部用本地服务器，不访问外网。
